# 手机配对问题（分析，不是规格）

状态：问题分析。不替代 `LoFiClaude_PRD_MOBILE_PAIRING.md` 和 `MOBILE_PAIRING_TECHNICAL_PLAN.md`。完成状态仍以根目录 `HANDOFF.md` 为准。

## 结论

**不是必须有公网。**

公网中转只是让「iPhone 系统相机 → Safari」一定能打开的一种办法。LoFiClaude 当前扫码失败，是因为二维码把 **地址** 和 **钥匙** 焊在一张会过期的局域网 HTTP 图上；不是因为没做成 Mac App，也不是因为本机 Clash 系统代理。

现有 PRD 的非目标已经写了：不做云端账号、远程公网访问。要 ZCode 那种「扫一下就进」，等于改这条非目标。先决定产品，再改实现。

## 扫码实际只做一件事

手机必须把 TCP 打到二维码里的主机，然后 `GET` 到页面。这一跳成立，Safari 才会打开。token、WebSocket、Origin 都还没开始。

当前码的形状：

```text
http://{电脑LAN IPv4}:9121/mobile.html?token={一次性凭证}
```

电脑上实际是两段互不等价的服务：

```text
电脑浏览器 ──► 127.0.0.1:9121     Bridge 一启动就在（管理口）
手机 Safari ──► {LAN IP}:9121     只有点过「连接手机」且未过期才在
```

二维码印的是第二条。默认、过期、或 LAN 未 bind 时，Safari 的结果就是无法打开网页。2026-09-13 在本机验证：LAN 未开启时直连 `192.168.155.8:9121` 立即被拒；`POST /pairing/start` 之后同一地址 HTTP 200。

本机 Clash Party 为系统代理、TUN 关闭、`192.168.0.0/16` 已绕过时，**不是** 这条失败的主因。iPhone 访问字面量局域网 IP 不经过电脑上的代理。会搞坏配对的是电脑开 TUN，或手机自己开全局代理。`allow-lan: false` 只管 Clash 的 7890，不管 9121。

## 失败被设计成同一种外观

配对要同时满足三件事，当前实现把它们焊死了：

1. **安全**：默认不把控制面暴露到局域网。
2. **发现**：唯一入口是一张印着字面量 IPv4 的图。
3. **可达**：假设同一 Wi-Fi 等于同一二层，且扫码当下端口一定在听。

焊在一起之后，下面每一种失败，用户看到的都是「Safari 打不开」：

| 真实原因 | 用户看到 |
|----------|----------|
| 没点「连接手机」，或二维码过期 | 打不开 |
| 路由器访客隔离 / 客户端隔离 | 打不开 |
| iOS 拒绝「本地网络」 | 打不开 |
| 电脑防火墙丢入站 | 打不开 |
| 手机全局代理把 `192.168.*` 送走 | 打不开 |

桌面生成 QR 时没有探测「这个 IP 从非本机是否可达」，也没有分层错误。一次性 token、WS Origin、hash 丢失会造成「页开了、停在正在连接电脑」，**不会**造成「自带浏览器打不开」。

「同一 Wi-Fi」在物理上也不等于可连。访客网络、AP isolation、iPhone 热点客户端隔离，都是同一 SSID、二层不通。

## ZCode 为什么扫一下就行

对照物是智谱 ZCode 桌面端的「移动端远程控制」，不是 LocalSend。

ZCode 二维码打开的是公网 HTTPS，形如：

```text
https://zcode.z.ai/remote/v4?sid=…&hash=…&t=…&mid=…&name={电脑主机名}&app_version=…
```

Safari 访问的是 `zcode.z.ai`，和打开普通网站一样。查询参数里的 `name=Eliot-898.local` 只是展示哪台电脑，**连接不走这个主机名，也不走局域网 IP。** 弹窗「等待手机连接 · 已就绪」表示电脑已经连上中转，在等手机拿钥匙进来。刷新二维码作废的是凭证，不是重绑网卡。

链路：

```text
ZCode:       手机 ──HTTPS──► zcode.z.ai ──中转──► 已联网的 ZCode.app（电脑主动连出去）
LoFiClaude:  手机 ──HTTP───► 192.168.x.x:9121（电脑在局域网等人进来）
```

Mac App 在 ZCode 里的作用是进程常驻、出站连中转、弹出公网码。扫码顺，是因为 **QR = 公网网址 + 密钥**。把 LoFiClaude 包成 `.app`、QR 仍是 `http://192.168.x.x:9121`，iPhone 还是打不开。

四个随机码如果出现，也是钥匙，不是地址。Steam Link 的 PIN、飞书 `/bind` 同理：先有可达通道，再用短码确认身份。

## 什么时候才必须公网

只有同时坚持下面三条，才必须有一个公网入口（自建中转、产品云，或隧道）：

1. 手机不装 App，只用系统相机和 Safari。
2. 用户不能接受「同一普通 Wi-Fi、关掉访客隔离、允许本地网络」这种环境条件。
3. 扫码必须像打开 https 网站一样，在 4G / 访客网 / 电脑开了 TUN 时也成功。

ZCode 选了这三条，所以必须有 `zcode.z.ai`。LoFiClaude 当前规格没有选第 2、第 3 条。

## 不必公网的做法

发现和鉴权拆开。端口在用户点「连接手机」之后保持可连，直到主动停止；QR 只当钥匙。失败分成「打不开 / 找不到 / 未授权」。

| 做法 | 要公网吗 | 手机侧 | 代价 |
|------|----------|--------|------|
| 修现有 LAN：意图期间一直听、倒计时与套接字一致、可复制链接、错误分层 | 否 | 仍是 Safari + HTTP | 仍受 AP 隔离、iOS 本地网络限制 |
| mDNS / Bonjour（`loficlaude.local`） | 否 | Safari 仍可能要本地网络权限 | 电脑能广播；纯网页手机听不到组播 |
| 两端 App（LocalSend / KDE Connect） | 否 | 必须有 iOS/Android 客户端 | 真发现 + 真 PIN；工作量是另一条产品线 |
| 电脑出站隧道（Cloudflare / Tailscale），QR 变成 `https://…` | 要一个出口，不必自建产品云 | Safari 当网站打开 | Mac 壳在这里才有用：方便跑隧道 |
| 产品中转（ZCode 同款） | 是 | 扫一下就进 | 会话经过第三方，直接违反现行配对非目标 |

Mac App 能加的是电脑侧：Bridge 常驻、本机音频、防火墙显示应用名、意图期间端口一直开、需要时拉起隧道。它加不到：Safari 听组播、Safari 穿透 AP 隔离、无公网时在 4G 上打开房间。

## 和现行规格的关系

`LoFiClaude_PRD_MOBILE_PAIRING.md` 非目标包含云端账号和远程公网访问。`MOBILE_PAIRING_TECHNICAL_PLAN.md` 规定默认只听 `127.0.0.1`，LAN 为显式、临时、5 分钟、一次性 token。

这套规格在安全上说得通，在「第一次用系统相机扫码」上不友好。实现基本按规格在跑；扫码失败是这个模型的默认态，不是偶发环境毛刺。

未决的是产品选择，不是再猜 Clash：

1. 守本地直连：收配对窗口（意图期间端口常开、QR 只当钥匙、分层错误），真机再扫。
2. 要 ZCode 体验：先改非目标，接受中转或隧道，再谈壳。
3. 不要为了扫码先做 Mac App。壳解决房间常驻和音频，不解决 `http://192.168.x.x` 这一跳。
